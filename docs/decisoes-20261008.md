## Multi-user security (spec for v0.1.0)
1. No identity or secret in the image. The CI runs gitleaks on the layers.
2. Volumes and caches named per user and project (`<user>-<project>-op`, cache, `~/.claude`). A shared volume never holds a secret.
3. The host Docker socket is root on the host: only on a single-owner machine. On runners and shared machines use rootless, sysbox or no socket. It is an option, **off by default**.
4. The owner's 1Password SSH agent never enters an automation container or another user's. Automation uses the bot identity with `OP_BIOMETRIC_UNLOCK_ENABLED=false`.
5. Container name `<project>-<user>`, without a fixed `--name`. Compose project name per user.
6. uid from the host (`updateRemoteUserUID`). sudo only to match the socket group.
7. Least-scope credential: one SA per project, read-only. One revocable token per runner. An all-vaults credential never goes into a daily-use container.
8. Supply chain: versions and digests pinned, published only by CI from a tag, signed (cosign). The project references by digest.
9. Ports on `127.0.0.1`. Runners: egress only to what the job needs.
10. Audit by actor (`audit.log` of `tars secrets`, commits).
11. Mounts of other projects are read-only, with the path coming from the user, never a fixed `/home/pablo`.

## Parity with CI (GitHub Actions; GitLab later)
- The CI runs **in the same image** by digest: `devcontainers/ci` on GitHub, `image:` on GitLab.
- **A single entrypoint** (`task ci`), with a thin YAML. The local pre-push runs the same `task ci`.
- Same compose, same variable **names**, test discovery done by the runner (no shell glob: the `npm test` on Windows ran 1 file).
- Declared differences: multi-arch; DinD in CI; Windows-only tests in a `windows-latest` job; TZ=UTC and LANG=C.UTF-8 pinned.
- **Parity gate in `tars doctor`:**
  - the image/digest in the CI equals the one in the devcontainer;
  - the CI calls only the entrypoint;
  - service versions match.
- GitLab = a YAML generator in the Tars from the same declaration.
